# Conditional WiFi Reconnect + Wired-Connection Awareness

## What

Two related additions:

1. **Wired-connection awareness (one-time, boot-time check, in `start.sh`).** Extend the existing boot-time gate in `start.sh` (currently `iwgetid -r`, which skips launching wifi-connect if WiFi is already connected) to also skip launching wifi-connect if a wired (Ethernet) connection is already up. This is a single check made once, before wifi-connect ever runs — no polling, and no changes inside the Rust binary. If the wired interface is present but still negotiating DHCP at that moment, the check waits up to a short, bounded timeout for it to finish activating (mirroring the existing bounded `sleep 15` wait already used for the WiFi check) before concluding wired is not up. If wired is still not up once that timeout elapses, wifi-connect launches and behaves exactly as it does today with respect to wired.
2. **Periodic conditional reconnect (inside `src/network.rs`, while the AP is running).** Once wifi-connect has launched and created the AP (which per (1) only happens when neither WiFi nor wired was up at boot), periodically attempt to reconnect to previously-saved WiFi networks that are currently visible in a scan, trying them in order of most-recently-connected first and walking backward through connection history. Reuse the existing single-attempt connect flow (stop AP → attempt connect → wait for connectivity → success exits, failure restores AP). This loop is WiFi-only and does not re-check wired state at any point. "Most-recently-connected" is tracked by wifi-connect itself in a small local cache file (see AC3/AC5 below) — not read from NetworkManager's own connection metadata.

## Why

- Loci devices in the field sometimes lose WiFi from a transient cause (router reboot, temporary move out of range) and are left showing the captive portal until a human re-enters credentials NetworkManager already has saved. Auto-retrying saved networks removes that manual step in the common case.
- When a Loci has a working wired connection, keeping a WiFi AP up is unnecessary — it ties up the radio and leaves a confusing/unwanted open AP broadcasting. The AP should stand aside whenever wired is genuinely up.

## Acceptance criteria

1. At boot, `start.sh` checks for an active wired connection in addition to its existing WiFi check; if either is already up, wifi-connect is not launched at all (current behavior for WiFi is preserved; wired is added as an equivalent condition). If the wired interface is still negotiating DHCP, the check waits up to a bounded timeout before concluding wired is not up (see "What" above).
2. This wired check happens exactly once, before wifi-connect launches. There is no polling of wired state afterward — neither inside `start.sh` nor inside the running wifi-connect process. wifi-connect's own code has no wired-awareness at all.

    _Note: this is a deliberate simplification for now (see Non-goals) — treating wired-state changes as boot-time-only, in both directions, may be worth revisiting later if it proves too coarse in the field (e.g. a device that's frequently plugged/unplugged post-boot)._

3. While the AP portal is running (which, per (1), only happens when neither WiFi nor wired was up at boot), wifi-connect attempts, on a fixed interval (default 30 minutes), to connect to NetworkManager connection profiles for networks that are both currently visible in the latest WiFi scan and have a saved profile, in descending order of last-successful-connection time as recorded in wifi-connect's own local cache (most recent first, unrecorded networks sorted last), stopping at the first success.
4. Each reconnect attempt reuses the existing connect-and-verify-connectivity flow (stop AP → attempt connection → wait for connectivity up to the existing timeout), and on success exits wifi-connect the same way a manual captive-portal submission would.
5. Every successful WiFi connection — whether from a manual captive-portal submission or a periodic reconnect attempt — records that SSID and the current time in a local cache at `/data/reconnect-history.json` (path fixed by [ADR 0008](/opt/adi/adr/0008-per-service-volume-standardized-data-mount.md); see also this repo's `docs/adr/0001-per-service-volume-standardized-data-mount.md`), so ordering improves as wifi-connect itself makes more successful connections over time. Writes are atomic (write-temp-then-rename) so a power loss mid-write (no UPS on these devices) cannot corrupt the file; a missing or corrupt cache file is treated as empty history, never a crash. The cache is written only on a successful connection — not on every periodic tick or failed attempt — to minimize wear on the underlying SD/eMMC storage.
6. If every candidate in a reconnect cycle fails, the AP portal is recreated and wifi-connect resumes waiting for the next periodic cycle or a manual captive-portal submission, as if the cycle had not run.
7. A reconnect cycle with no in-range saved-network candidates is a no-op — it does not tear down or disturb the AP — **except on a forced-rescan cycle (AC11), where the scan is refreshed regardless of what the previous cached scan showed.**
8. Manual captive-portal connect requests continue to work unchanged. A reconnect cycle and a manual submission never run concurrently; whichever starts first runs to completion (no preemption either direction). This is an accepted, documented minor UX limitation, not a bug.
9. The periodic reconnect interval, and whether the feature is enabled at all, are configurable via a CLI flag / env var following the existing `--portal-*` pattern in `config.rs`, under a shared `RECONNECT_*` prefix: `--reconnect-enabled` / `$RECONNECT_ENABLED` (default `true`) and `--reconnect-interval-minutes` / `$RECONNECT_INTERVAL_MINUTES` (default `30`). Exact flag names finalized in planning.
10. `README.md` is not modified by this work. A new document is added under `docs/` giving a high-level overview of how wifi-connect works end-to-end (startup → AP creation → portal → connect attempt → exit), covering both the new `start.sh` wired check and the periodic-reconnect behavior. It is written in the same style as the existing `docs/*.md` files.
11. **Forced periodic rescan (closes the "stale boot-time scan" gap).** The WiFi scan backing candidate selection (AC3) is cached and, per AC6/AC7, normally only refreshed as a side effect of an attempted reconnect. Left uncorrected, this means a network absent from the scan at boot (e.g. its router was mid-reboot at that exact moment — the spec's own motivating scenario) is *never* retried, because "no candidates" never triggers a rescan and "no rescan" never produces a candidate — a permanent no-op regardless of what actually happens on the network afterward. To close this: every Nth periodic reconnect tick (`N` = `$RECONNECT_RESCAN_EVERY`, default `2` — i.e. effectively every 2×`RECONNECT_INTERVAL_MINUTES` minutes by default) is a **forced-rescan tick**: the AP is stopped, a fresh scan is taken, and candidates are recomputed from that fresh scan *before* deciding whether there's anything to try — regardless of what the previous cached scan showed. This means the AP is briefly stopped and immediately recreated on forced-rescan ticks even when the fresh scan still finds nothing, which is the deliberate, narrow exception to AC7 stated above. Non-forced ticks are unchanged from AC3-AC7's existing behavior. Setting `$RECONNECT_RESCAN_EVERY` to `0` disables forced rescanning entirely, reverting to the pre-existing (gap-having) behavior, for anyone who needs AC7's "never disturbed" guarantee to hold unconditionally.

## Non-goals

- Any dynamic reaction to a wired connection state change after the initial boot-time check in `start.sh` — this covers both directions symmetrically: wired coming up while the AP is already running (does not tear it down), and wired going down after wifi-connect has already exited because wired was up at boot (does not relaunch wifi-connect). Both are one-time, boot-time-only decisions; anything after that requires an external relaunch (supervision/restart policy), which is out of scope for this feature. Flagged in AC2 as a simplification worth revisiting later.
- Making wifi-connect resident/never-exiting — it keeps its current "exit on success" lifecycle unchanged.
- Debounce/hysteresis for a rapidly flapping Ethernet link — moot now that there's no polling of wired state at all.
- Retrying hidden (non-broadcasting) saved networks or any network not currently visible in a scan.
- Any change to the manual captive-portal connect flow's UX or HTTP API.
- Editing `README.md` — a separate `docs/` file is added instead; whether to add a single cross-link line from README is a follow-up decision, not bundled into this change.
- Reading NetworkManager's own `connection.timestamp` property (which upstream's `network-manager` crate doesn't expose) or vendoring/patching that crate to get at it — considered and rejected in favor of wifi-connect maintaining its own small cache; see [ADR 0008](/opt/adi/adr/0008-per-service-volume-standardized-data-mount.md) for the persistence-layout rationale.
- A configurable path for the history cache file — it's fixed at `/data/reconnect-history.json` per ADR 0008; no CLI flag/env var for it.

## Interface / config additions (indicative — exact names finalized in planning)

- `--reconnect-enabled` / `$RECONNECT_ENABLED` (default `true`) — opts out of periodic reconnect entirely when set to `false`.
- `--reconnect-interval-minutes` / `$RECONNECT_INTERVAL_MINUTES` (default `30`) — interval between reconnect cycles.
- `--reconnect-rescan-every` / `$RECONNECT_RESCAN_EVERY` (default `2`) — every Nth periodic tick forces a fresh WiFi scan regardless of cached candidates (AC11); `0` disables forced rescanning entirely.
- All three share the `RECONNECT_*` prefix/namespace, following the existing `--portal-*` / `$PORTAL_*` convention in `config.rs`.
- `start.sh`'s wired check needs no new wifi-connect flag — it's a pure shell-side gate (e.g. checking for a default route or `Activated` wired device via `nmcli`/`ip`, with a bounded wait for DHCP negotiation), decided before wifi-connect is invoked at all.
- No new flag for the reconnect-history cache path — hardcoded to `/data/reconnect-history.json` per ADR 0008; a dedicated Docker volume mounted at `/data` for the wifi-connect service is a companion change in `loci-on-balena` (outside this repo).
